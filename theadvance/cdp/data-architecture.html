Section 01

Tổng quan kiến trúc

Nguyên tắc thiết kế và kiến trúc tổng thể của CDP TheAdvance.

1.1. Nguyên tắc thiết kế

01
ClickHouse là trung tâm

Mọi data đều chảy về ClickHouse, không lưu trữ chính ở nơi khác.

02
Raw trước, Transform sau

Luôn lưu data thô gốc trước, rồi mới transform/enrich.

03
Schema-on-write

Data ghi vào ClickHouse phải đúng schema, validate trước khi insert.

04
Idempotent ingestion

Mọi cơ chế đều có thể retry mà không tạo duplicate.

05
Lineage tracking

Mỗi record biết mình đến từ đâu, qua cơ chế nào, lúc nào.

Bốn cơ chế đồng bộ dữ liệu

So sánh và chi tiết từng cơ chế ingestion về ClickHouse.

2.1. Tổng quan so sánh

Cơ chế 1: ETL (Airbyte) Cơ chế 2: Kafka Realtime Cơ chế 3: API Pull Cơ chế 4: API Gateway Write
Mô hình Batch pull từ nguồn → transform → load Stream event realtime Scheduled pull từ API Push trực tiếp vào CDP
Latency Phút → giờ Giây Phút → giờ Giây (real-time)

2.2. Cơ chế 1: ETL via Airbyte

Mục đích: Đồng bộ batch data từ database/file của các hệ thống nguồn về ClickHouse.

Flow chi tiết

┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Source DB   │     │   Airbyte    │     │  ClickHouse  │     │  Transform   │
│  (POS, CRM,  │────▶│   Extract    │────▶│  raw_* table │────▶│  Job (dbt/   │
│   ERP, CSV)  │     │  & Load      │     │  (Bronze)    │     │  MV/cron)    │
└──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘

Nguồn áp dụng

Nguồn BU Data Tần suất sync Sync mode
POS Database (MySQL/PostgreSQL) ND, Zema Khách hàng, giao dịch, dịch vụ, liệu trình, lịch hẹn */15 * * * * Incremental (CDC/cursor)
CRM Database Cả 3 Lead, contact, deal, activity Mỗi 15 phút Incremental
ERP Database Ocany Đơn hàng, sản phẩm, kho, công nợ Mỗi giờ Incremental
DMS Database Ocany Đại lý, sell-out, tồn kho NPP Mỗi giờ Incremental
Excel/CSV (manual upload) Cả 3 Data lịch sử, import 1 lần On-demand Full refresh
Google Sheets Cả 3 Mapping tables, config Daily Full refresh

Airbyte configuration

yaml 
# Ví dụ: Sync POS Ngọc Dung
source:
  type: mysql
  host: pos-ngocdung-db.internal
  database: pos_production
  tables:
    - customers        # Khách hàng
    - transactions     # Giao dịch
    - transaction_items # Chi tiết giao dịch
    - services         # Danh mục dịch vụ
    - appointments     # Lịch hẹn
    - treatments       # Liệu trình
    - treatment_sessions # Buổi liệu trình

destination:
  type: clickhouse
  host: clickhouse-cdp.internal
  database: cdp_raw

sync:
  mode: incremental_append_dedup
  cursor_field: updated_at
  primary_key: id
  frequency: "*/15 * * * *"  # Mỗi 15 phút

Metadata columns (Airbyte tự thêm)

Mỗi raw table đều có các cột metadata:

ColumnTypeMô tả
_airbyte_raw_idStringUUID unique cho mỗi record ingested
_airbyte_extracted_atDateTime64Thời điểm Airbyte extract từ nguồn
_airbyte_loaded_atDateTime64Thời điểm load vào ClickHouse
_airbyte_sourceStringTên connection (VD: pos_ngocdung)
_airbyte_generation_idUInt64Sync generation (để track full refresh vs incremental)

Xử lý dedup

Airbyte chạy incremental có thể tạo duplicate (cùng record extract nhiều lần). Xử lý bằng ReplacingMergeTree:

sql 
CREATE TABLE cdp_raw.raw_pos_ngocdung_customers
(
    id                    UInt64,
    name                  String,
    phone                 String,
    email                 Nullable(String),
    gender                Nullable(String),
    dob                   Nullable(Date),
    branch_id             Nullable(UInt32),
    created_at            DateTime64(3),
    updated_at            DateTime64(3),
    -- Airbyte metadata
    _airbyte_raw_id       String,
    _airbyte_extracted_at DateTime64(3),
    _airbyte_loaded_at    DateTime64(3),
    _airbyte_source       LowCardinality(String)
)
ENGINE = ReplacingMergeTree(_airbyte_loaded_at)
ORDER BY (id)
PARTITION BY toYYYYMM(created_at);

Monitoring & alerting

  • Airbyte dashboard: theo dõi status mỗi connection
  • Alert khi sync fail > 2 lần liên tiếp
  • Alert khi sync chậm hơn SLA (VD: POS sync > 30 phút)
  • Alert khi số record sync = 0 (nguồn có thể die)
  • Daily report: tổng record synced per source

Dead Letter Queue

Event không parse được hoặc không đúng schema → đẩy vào DLQ topic:

cdp.events.dlq   ←── Events bị reject (schema invalid, parse error)

Consumer riêng ghi vào cdp_raw.raw_events_dlq. Admin dashboard: xem DLQ count, lý do reject, retry manual.

Worker design

Mỗi API source có 1 worker riêng, chạy dưới dạng scheduled job:

python 
# Pseudo-code cho mỗi worker
class APIWorker:
    def run(self):
        # 1. Lấy checkpoint (last sync cursor)
        checkpoint = get_checkpoint(self.source_name)

        # 2. Pull data từ API (pagination)
        raw_data = self.pull_from_api(since=checkpoint.last_cursor)

        # 3. Validate schema
        valid, invalid = self.validate(raw_data)

        # 4. Ghi invalid vào DLQ table
        if invalid:
            insert_to_dlq(invalid, reason="schema_validation_failed")

        # 5. Ghi valid vào raw table
        insert_to_clickhouse(
            table=f"cdp_raw.raw_api_{self.source_name}_{self.bu}",
            data=valid
        )

        # 6. Cập nhật checkpoint
        update_checkpoint(self.source_name, new_cursor)

        # 7. Log metrics
        log_metrics(source=self.source_name, pulled=len(raw_data),
                    valid=len(valid), invalid=len(invalid))

Chuẩn hoá dữ liệu

Data Standardization — xử lý sự khác biệt format giữa các nguồn.

3.1. Vấn đề: Mỗi nguồn có format khác nhau

example 
Cùng 1 khách "Nguyễn Thị A" xuất hiện ở 5 nguồn:

POS Ngọc Dung:  { phone: "+84901234567", name: "NGUYỄN THỊ A", gender: "F" }
CRM Zema:       { sdt: "0901.234.567", ho_ten: "Nguyễn Thị A", gioi_tinh: "Nữ" }
ERP Ocany:      { mobile: "84901234567", customer_name: "Nguyen Thi A", sex: 2 }
Facebook Lead:  { phone_number: "0901 234 567", full_name: "A Nguyễn" }
Website form:   { tel: "0901234567", name: "chị A" }

3.2. Standardization Rules

3.2.1. Phone number

rules 
Input bất kỳ → Output chuẩn: 0901234567 (10 số, bắt đầu bằng 0)

Rules:
1. Loại bỏ mọi ký tự không phải số: spaces, dashes, dots, brackets
2. Bỏ prefix quốc gia:
   - "+84" → "0"
   - "84" (đầu) → "0"
   - "0084" → "0"
3. Validate:
   - Phải 10 số (sau chuẩn hoá)
   - Bắt đầu bằng 0
   - Prefix hợp lệ: 03x, 05x, 07x, 08x, 09x
4. Nếu không hợp lệ → giữ nguyên raw + flag invalid

Ví dụ:
  "+84901234567"  → "0901234567" ✅
  "0901.234.567"  → "0901234567" ✅
  "84901234567"   → "0901234567" ✅
  "0901 234 567"  → "0901234567" ✅
  "901234567"     → "0901234567" ✅ (thêm 0 đầu nếu 9 số)
  "1234567"       → "1234567" ❌ (flag invalid, giữ raw)
  "0000000000"    → blacklist, không dùng cho identity resolution

3.2.2. Email

rules 
Input bất kỳ → Output chuẩn: lowercase, trimmed

Rules:
1. Trim whitespace
2. Lowercase toàn bộ
3. Validate format: regex email chuẩn
4. Loại bỏ email rõ ràng fake:
   - test@test.com, example@example.com
   - abc@abc.com, no@email.com
   - Domain không tồn tại (optional, nếu có DNS check)

Ví dụ:
  " A.Nguyen@Gmail.COM "  → "a.nguyen@gmail.com" ✅
  "nguyen thi a@yahoo"    → invalid ❌

3.2.3. Customer name

rules 
Input bất kỳ → Output chuẩn: Title Case, trimmed, normalized

Rules:
1. Trim whitespace, collapse multiple spaces
2. Remove prefix/suffix: "chị", "anh", "cô", "Mr.", "Mrs.", "Ms."
3. Title Case: "nguyễn thị a" → "Nguyễn Thị A"
4. Chuẩn hoá dấu tiếng Việt: NFD → NFC
5. Giữ nguyên raw name, tạo thêm field normalized_name

Ví dụ:
  "NGUYỄN THỊ A"     → "Nguyễn Thị A"
  "nguyen thi a"      → "Nguyen Thi A" (không có dấu → giữ không dấu)
  "chị A Nguyễn"      → "A Nguyễn" (bỏ "chị", giữ thứ tự gốc)
  "  Nguyễn  Thị   A" → "Nguyễn Thị A" (collapse spaces)

3.2.4. Gender

rules 
Input bất kỳ → Output chuẩn: 'M' | 'F' | null

Mapping:
  'F', 'female', 'nữ', 'nu', 'Nữ', 2, '2', 'woman' → 'F'
  'M', 'male', 'nam', 'Nam', 1, '1', 'man'          → 'M'
  Mọi giá trị khác                                   → null

3.2.5. Date of birth

rules 
Input bất kỳ → Output chuẩn: Date (YYYY-MM-DD)

Formats accepted:
  "1990-05-15"     → 1990-05-15 ✅
  "15/05/1990"     → 1990-05-15 ✅
  "05/15/1990"     → 1990-05-15 ✅ (detect US format)
  "15-05-1990"     → 1990-05-15 ✅
  "1990"           → 1990-01-01 (chỉ có năm → ghi nhận năm, flag partial)
  "May 15, 1990"   → 1990-05-15 ✅

Validation:
  - Năm sinh: 1920-2015 (hợp lý cho khách hàng)
  - Ngoài range → flag suspicious, giữ raw

3.2.6. Address

rules 
Input bất kỳ → Output: structured address

Fields:
  - raw_address: String (giữ nguyên)
  - province: String (tỉnh/thành phố, chuẩn hoá theo danh mục 63 tỉnh)
  - district: String (quận/huyện, chuẩn hoá)
  - ward: String (phường/xã, chuẩn hoá)
  - street: String (phần còn lại)
  - region: String (Bắc/Trung/Nam, tự derive từ province)

Mapping table: cần bảng danh mục hành chính VN chuẩn

3.2.7. Currency / Amount

rules 
Input bất kỳ → Output chuẩn: Decimal64(2), đơn vị VND

Rules:
1. Loại bỏ ký tự: "VND", "đ", "₫", ",", "."
2. Detect separator:
   - "1.500.000" → 1500000 (dấu . là thousand separator VN)
   - "1,500,000" → 1500000 (dấu , là thousand separator)
   - "1500000.50" → 1500000.50 (dấu . cuối là decimal)
3. Validate: amount > 0 và hợp lý (< 100 tỷ)

3.2.8. Timestamp

rules 
Input bất kỳ → Output chuẩn: DateTime64(3), UTC timezone

Rules:
1. Parse multiple formats: ISO 8601, Unix epoch (sec & ms), custom formats
2. Convert timezone:
   - Nếu có timezone info → convert sang UTC
   - Nếu không có → assume Asia/Ho_Chi_Minh (UTC+7) → convert sang UTC
3. Validate: không quá xa trong tương lai (> now + 1 day → reject)
   Không quá xa trong quá khứ (tuỳ context: events < 1 năm, transactions < 10 năm)

Ví dụ:
  "2026-06-11T14:30:00+07:00" → "2026-06-11T07:30:00.000Z"
  "2026-06-11 14:30:00"       → "2026-06-11T07:30:00.000Z" (assume +7)
  1718107800                   → "2026-06-11T07:30:00.000Z"
  1718107800000                → "2026-06-11T07:30:00.000Z" (detect ms)

3.3. Standardization Pipeline

Mỗi data flow đều đi qua standardization trước khi vào Silver layer:

CREATE FUNCTION normalize_phone AS (raw_phone) ->
    if(
        length(
            replaceRegexpAll(
                replaceOne(
                    replaceOne(
                        replaceRegexpAll(toString(raw_phone), '[^0-9]', ''),
                    '840', '0'),  -- +840 → 0 (nếu 11 số)
                '84', '0'),       -- 84 → 0 (nếu 11 số bắt đầu 84)
            '^([3-9])', '0\\1')   -- thêm 0 nếu bắt đầu bằng 3-9
        ) = 10,
        replaceRegexpAll(
            replaceOne(
                replaceOne(
                    replaceRegexpAll(toString(raw_phone), '[^0-9]', ''),
                '840', '0'),
            '84', '0'),
        '^([3-9])', '0\\1'),
        NULL  -- invalid → null
    );

5.3. Data quality checks

Chạy sau mỗi transform:

sql 
-- Check: không có customer thiếu phone VÀ email
SELECT count(*) AS orphan_customers
FROM cdp_clean.customers
WHERE phone IS NULL AND email IS NULL;

-- Check: transaction amount hợp lý
SELECT count(*) AS suspicious_transactions
FROM cdp_clean.transactions
WHERE amount <= 0 OR amount > 10000000000;  -- > 10 tỷ

-- Check: data freshness — nguồn nào lâu không có data mới
SELECT
    source_system,
    bu,
    max(updated_at) AS last_data,
    dateDiff('hour', max(updated_at), now()) AS hours_stale
FROM cdp_clean.customers
GROUP BY source_system, bu
HAVING hours_stale > 24;

-- Check: duplicate rate sau identity resolution
SELECT
    phone,
    count(*) AS cnt
FROM cdp_clean.customers
WHERE phone IS NOT NULL
GROUP BY phone
HAVING cnt > 1;

Section 08

Checklist trước khi thiết kế schema chi tiết

Các điểm cần confirm trước khi bắt đầu implement schema production.

  • Confirm danh sách hệ thống nguồn thực tế của từng BU (POS nào? CRM nào? ERP nào?)
  • Confirm database type & version của từng hệ thống nguồn (MySQL? PostgreSQL? SQL Server?)
  • Confirm hệ thống nguồn nào có API/webhook, hệ thống nào chỉ export DB/CSV
  • Confirm data volume ước tính: số khách, số giao dịch/ngày, số event/ngày
  • Confirm ClickHouse deployment: self-hosted hay ClickHouse Cloud? Cluster hay single node?
  • Confirm Kafka deployment: self-managed hay managed (Confluent, AWS MSK)?
  • Confirm Airbyte deployment: OSS self-hosted hay Airbyte Cloud?
  • Review danh sách fields thực tế từ POS/CRM/ERP → adjust Silver schema
  • Xác nhận naming convention: tiếng Việt hay tiếng Anh cho business terms
  • Xác nhận timezone convention: UTC hay Asia/Ho_Chi_Minh
