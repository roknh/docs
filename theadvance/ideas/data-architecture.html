Data Architecture
& Ingestion Design

Kiến trúc dual-database — PostgreSQL làm operational brain (OLTP), ClickHouse làm analytical engine (OLAP). Hệ thống hoá 4 cơ chế đồng bộ và sync pattern giữa 2 database.

Version 2.0 Ngày 2026-06-12 OLTP PostgreSQL OLAP ClickHouse Streaming Kafka ETL Airbyte
Section 01

Tổng quan kiến trúc

Nguyên tắc thiết kế dual-database và kiến trúc tổng thể của CDP TheAdvance.

1.1. Nguyên tắc thiết kế

01
Dual-database: PG + ClickHouse

PostgreSQL cho operational data (ACID, point lookup, updates). ClickHouse cho analytics (columnar scan, bulk insert, fast aggregation). Mỗi database làm đúng thế mạnh.

02
PostgreSQL là source of truth

Customer profile, lead state, campaign state, consent sống ở PG. ClickHouse nhận bản replicate để phục vụ analytics, không là nơi ghi gốc.

03
Raw trước, Transform sau

Luôn lưu data thô gốc trước (ClickHouse Bronze layer), rồi mới transform/enrich. Không mất data gốc.

04
Schema-on-write

Data ghi vào cả PG và ClickHouse phải đúng schema, validate trước khi insert. Không schema-on-read.

05
Idempotent ingestion

Mọi cơ chế đều có thể retry mà không tạo duplicate. ReplacingMergeTree ở CH, UPSERT ở PG.

06
Lineage tracking

Mỗi record biết mình đến từ đâu, qua cơ chế nào, lúc nào. Trace được từ Gold về Bronze.

07
Sync unidirectional: PG → CH

Master data chảy 1 chiều từ PG sang CH qua CDC hoặc scheduled sync. ClickHouse không ghi ngược về PG — chỉ batch jobs đọc CH rồi write kết quả vào PG.

1.3. Tại sao Dual-Database?

Vấn đề ClickHouse only PostgreSQL + ClickHouse
Customer 360 lookup (WHERE id = X) Columnar scan, chậm cho single-row PG B-tree index, < 5ms
Update lead status ReplacingMergeTree + FINAL, không atomic UPDATE ... SET status = 'contacted', ACID
Consent on/off Insert new row, merge later, race condition UPDATE atomic, consistent ngay
Campaign state machine Không có transaction, dễ inconsistent Transaction: insert campaign + members + update segment
Identity merge/unmerge Không rollback được Transaction: merge 2 profiles atomic
Small concurrent writes (API identify, webhook) "Too many parts" error khi insert từng row PG handle hàng nghìn small writes/giây
Application config (users, roles, scoring rules) Overkill, không cần columnar PG relational model, JOIN, foreign key
Billion events analytics Columnar scan cực nhanh PG chết ở scale này
Dashboard aggregation SUM/AVG/COUNT trên 100M rows < 1 giây PG timeout
Time-series score history MergeTree partition by month, TTL tự xóa PG partition phức tạp hơn

Mục đích: Đồng bộ batch data từ database/file của các hệ thống nguồn về ClickHouse.

Xử lý dedup

Airbyte chạy incremental có thể tạo duplicate (cùng record extract nhiều lần). Xử lý bằng ReplacingMergeTree:

sql 
CREATE TABLE cdp_raw.raw_pos_ngocdung_customers
(
    id                    UInt64,
    name                  String,
    phone                 String,
    email                 Nullable(String),
    gender                Nullable(String),
    dob                   Nullable(Date),
    branch_id             Nullable(UInt32),
    created_at            DateTime64(3),
    updated_at            DateTime64(3),
    -- Airbyte metadata
    _airbyte_raw_id       String,
    _airbyte_extracted_at DateTime64(3),
    _airbyte_loaded_at    DateTime64(3),
    _airbyte_source       LowCardinality(String)
)
ENGINE = ReplacingMergeTree(_airbyte_loaded_at)
ORDER BY (id)
PARTITION BY toYYYYMM(created_at);

Monitoring & alerting

  • Airbyte dashboard: theo dõi status mỗi connection
  • Alert khi sync fail > 2 lần liên tiếp
  • Alert khi sync chậm hơn SLA (VD: POS sync > 30 phút)
  • Alert khi số record sync = 0 (nguồn có thể die)
  • Daily report: tổng record synced per source

Dead Letter Queue

Event không parse được hoặc không đúng schema → đẩy vào DLQ topic:

cdp.events.dlq   ←── Events bị reject (schema invalid, parse error)

Consumer riêng ghi vào cdp_raw.raw_events_dlq. Admin dashboard: xem DLQ count, lý do reject, retry manual.

Worker design

Mỗi API source có 1 worker riêng, chạy dưới dạng scheduled job:

python 
# Pseudo-code cho mỗi worker
class APIWorker:
    def run(self):
        # 1. Lấy checkpoint (last sync cursor)
        checkpoint = get_checkpoint(self.source_name)

        # 2. Pull data từ API (pagination)
        raw_data = self.pull_from_api(since=checkpoint.last_cursor)

        # 3. Validate schema
        valid, invalid = self.validate(raw_data)

        # 4. Ghi invalid vào DLQ table
        if invalid:
            insert_to_dlq(invalid, reason="schema_validation_failed")

        # 5. Ghi valid vào raw table
        insert_to_clickhouse(
            table=f"cdp_raw.raw_api_{self.source_name}_{self.bu}",
            data=valid
        )

        # 6. Cập nhật checkpoint
        update_checkpoint(self.source_name, new_cursor)

        # 7. Log metrics
        log_metrics(source=self.source_name, pulled=len(raw_data),
                    valid=len(valid), invalid=len(invalid))

Section 03

Chuẩn hoá dữ liệu

Data Standardization — xử lý sự khác biệt format giữa các nguồn.

3.1. Vấn đề: Mỗi nguồn có format khác nhau

example 
Cùng 1 khách "Nguyễn Thị A" xuất hiện ở 5 nguồn:

POS Ngọc Dung:  { phone: "+84901234567", name: "NGUYỄN THỊ A", gender: "F" }
CRM Zema:       { sdt: "0901.234.567", ho_ten: "Nguyễn Thị A", gioi_tinh: "Nữ" }
ERP Ocany:      { mobile: "84901234567", customer_name: "Nguyen Thi A", sex: 2 }
Facebook Lead:  { phone_number: "0901 234 567", full_name: "A Nguyễn" }
Website form:   { tel: "0901234567", name: "chị A" }

3.2. Standardization Rules

3.2.1. Phone number

rules 
Input bất kỳ → Output chuẩn: 0901234567 (10 số, bắt đầu bằng 0)

Rules:
1. Loại bỏ mọi ký tự không phải số: spaces, dashes, dots, brackets
2. Bỏ prefix quốc gia:
   - "+84" → "0"
   - "84" (đầu) → "0"
   - "0084" → "0"
3. Validate:
   - Phải 10 số (sau chuẩn hoá)
   - Bắt đầu bằng 0
   - Prefix hợp lệ: 03x, 05x, 07x, 08x, 09x
4. Nếu không hợp lệ → giữ nguyên raw + flag invalid

Ví dụ:
  "+84901234567"  → "0901234567" ✅
  "0901.234.567"  → "0901234567" ✅
  "84901234567"   → "0901234567" ✅
  "0901 234 567"  → "0901234567" ✅
  "901234567"     → "0901234567" ✅ (thêm 0 đầu nếu 9 số)
  "1234567"       → "1234567" ❌ (flag invalid, giữ raw)
  "0000000000"    → blacklist, không dùng cho identity resolution

3.2.2. Email

rules 
Input bất kỳ → Output chuẩn: lowercase, trimmed

Rules:
1. Trim whitespace
2. Lowercase toàn bộ
3. Validate format: regex email chuẩn
4. Loại bỏ email rõ ràng fake:
   - test@test.com, example@example.com
   - abc@abc.com, no@email.com

Ví dụ:
  " A.Nguyen@Gmail.COM "  → "a.nguyen@gmail.com" ✅
  "nguyen thi a@yahoo"    → invalid ❌

3.2.3. Customer name

rules 
Input bất kỳ → Output chuẩn: Title Case, trimmed, normalized

Rules:
1. Trim whitespace, collapse multiple spaces
2. Remove prefix/suffix: "chị", "anh", "cô", "Mr.", "Mrs.", "Ms."
3. Title Case: "nguyễn thị a" → "Nguyễn Thị A"
4. Chuẩn hoá dấu tiếng Việt: NFD → NFC
5. Giữ nguyên raw name, tạo thêm field normalized_name

Ví dụ:
  "NGUYỄN THỊ A"     → "Nguyễn Thị A"
  "nguyen thi a"      → "Nguyen Thi A"
  "chị A Nguyễn"      → "A Nguyễn" (bỏ "chị")
  "  Nguyễn  Thị   A" → "Nguyễn Thị A"

3.2.4–3.2.8. Gender, DOB, Address, Currency, Timestamp

rules 
-- Gender: 'F', 'female', 'nữ', 2, '2' → 'F' | 'M', 'male', 'nam', 1 → 'M' | else → NULL

-- DOB: "15/05/1990" | "1990-05-15" | "May 15, 1990" → Date(YYYY-MM-DD)
--      Validate năm: 1920–2015

-- Address: raw_address → {province, district, ward, street, region}
--          region = Bắc/Trung/Nam derived từ province

-- Currency: "1.500.000 VND" | "1,500,000đ" → Decimal64(2) 1500000.00

-- Timestamp: ISO 8601, Unix epoch(sec/ms), custom → DateTime64(3) UTC
--            Nếu không có timezone → assume Asia/Ho_Chi_Minh (UTC+7)
-- Ví dụ: "2026-06-11T14:30:00+07:00" → "2026-06-11T07:30:00.000Z"

Mỗi data flow đều đi qua standardization trước khi vào Silver layer:

│  Raw     │     │  Standard-  │     │  Validation  │     │  Silver  │

-- Ví dụ: function chuẩn hoá SĐT
CREATE FUNCTION normalize_phone AS (raw_phone) ->
    if(
        length(
            replaceRegexpAll(
                replaceOne(
                    replaceOne(
                        replaceRegexpAll(toString(raw_phone), '[^0-9]', ''),
                    '840', '0'),  -- +840 → 0 (nếu 11 số)
                '84', '0'),       -- 84 → 0 (nếu 11 số bắt đầu 84)
            '^([3-9])', '0\\1')   -- thêm 0 nếu bắt đầu bằng 3-9
        ) = 10,
        replaceRegexpAll(
            replaceOne(
                replaceOne(
                    replaceRegexpAll(toString(raw_phone), '[^0-9]', ''),
                '840', '0'),
            '84', '0'),
        '^([3-9])', '0\\1'),
        NULL  -- invalid → null
    );

5.3. Transform pipeline

CONTINUOUS (real-time)
[ClickHouse]
Kafka → raw_events (MV)
raw_events → cleaned events (MV: standardize timestamp, enrich)

[PG → CH CDC]
PG customers change → Debezium → Kafka → CH customers_replica
PG customer_scores change → Debezium → Kafka → CH scores_replica
FREQUENT (mỗi 15 phút)
Job: sync_customers_to_pg
  READ: CH raw_pos_*_customers + raw_crm_*_contacts
  Standardize: phone, email, name, gender, dob, address
  Run identity resolution (match & merge)
  WRITE: PG customers (UPSERT) ← source of truth
       └── CDC auto-syncs PG → CH customers_replica

Job: sync_transactions_to_ch
  READ: CH raw_pos_*_transactions + raw_erp_*_orders
  Standardize: amount, timestamp, channel
  Link customer_id (lookup PG identity_graph)
  WRITE: CH cdp_clean.transactions

Job: sync_leads_to_pg
  READ: CH raw_crm_*_leads + raw_api_facebook_leads
  Standardize + dedup + auto-assign + calculate lead score
  WRITE: PG leads (UPSERT) ← source of truth
HOURLY
Job: update_engagement_scores
  READ: CH events last 90 days per customer
  Apply scoring rules + decay (config from PG scoring_configs)
  WRITE: PG customer_scores.engagement_score (UPDATE)
       └── CDC auto-syncs to CH

Job: update_health_scores → WRITE: PG customer_scores.health_score

Job: refresh_segments
  Re-evaluate dynamic segment conditions (PG segment definitions)
  Some conditions query CH (spend > X, events in 30d)
  WRITE: PG segment_members (UPSERT)
DAILY (2:00 AM)
Job: calculate_scores_full
  READ: CH transactions + events (aggregate per customer)
  Full recalculate: monetary, loyalty, social scores, tier
  WRITE: PG customer_scores (full UPDATE)
  WRITE: CH customer_score_history (daily snapshot, append)

Job: calculate_rfm
  READ: CH transactions per BU
  WRITE: PG customer_scores.rfm_* (UPDATE)
  WRITE: CH rfm_results (snapshot)

Job: build_unified_customers_mv
  READ: PG customers + scores (via CH replica) + CH transaction aggregates
  WRITE: CH cdp_analytics.unified_customers_mv (full rebuild)

Job: aggregate_daily_metrics → WRITE: CH daily_*_metrics tables (append)
Job: sync_treatment_status → WRITE: PG treatments + sessions (UPSERT)
Job: update_dealer_health (Ocany) → WRITE: PG dealers.health_score
WEEKLY
Job: retrain_predictive_models
  READ: CH transactions + events (training data)
  READ: PG customers + scores (labels)
  Train: Churn, Upsell, Cross-BU models
  WRITE: PG customer_scores.churn_*/upsell_*/crossbu_*

Job: calculate_cohort_retention → CH
Job: calculate_ltv → CH + PG
Job: full_refresh_ch_replicas (safety net)
  Full dump PG customers/scores/branches → CH replicas

5.4. Data quality checks

sql 
-- PostgreSQL checks
-- Check: không có customer thiếu phone VÀ email
SELECT count(*) AS orphan_customers
FROM customers
WHERE phone IS NULL AND email IS NULL AND merged_into_id IS NULL;

-- Check: duplicate phone (should be 0 due to unique constraint)
SELECT phone, count(*) AS cnt
FROM customers
WHERE phone IS NOT NULL AND merged_into_id IS NULL
GROUP BY phone HAVING count(*) > 1;

-- Check: orphan scores
SELECT count(*) FROM customer_scores cs
LEFT JOIN customers c ON cs.customer_id = c.customer_id
WHERE c.customer_id IS NULL;

-- ClickHouse checks
-- Check: transaction amount hợp lý
SELECT count(*) AS suspicious_transactions
FROM cdp_clean.transactions
WHERE amount <= 0 OR amount > 10000000000;

-- Check: CH replica freshness vs PG
SELECT
    max(updated_at) AS ch_latest,
    dateDiff('minute', max(updated_at), now()) AS minutes_behind
FROM cdp_clean.customers_replica;

-- Check: data freshness per source
SELECT source_system, source_bu, max(timestamp) AS last_event,
    dateDiff('hour', max(timestamp), now()) AS hours_stale
FROM cdp_clean.events
GROUP BY source_system, source_bu
HAVING hours_stale > 24;

Section 08

Checklist trước khi thiết kế schema chi tiết

Các điểm cần confirm trước khi bắt đầu implement.

Infrastructure

  • Confirm PostgreSQL deployment: managed (RDS/Cloud SQL) hay self-hosted? Version ≥ 15?
  • Confirm ClickHouse deployment: self-hosted hay ClickHouse Cloud? Cluster hay single node?
  • Confirm Kafka deployment: self-managed hay managed (Confluent, AWS MSK)?
  • Confirm Airbyte deployment: OSS self-hosted hay Airbyte Cloud?
  • Confirm CDC tool: Debezium hay PG logical replication trực tiếp?
  • PG extensions cần cài: pg_trgm (fuzzy search), pgcrypto (PII masking), pg_stat_statements (monitoring)

Data sources

  • Confirm danh sách hệ thống nguồn thực tế của từng BU (POS nào? CRM nào? ERP nào?)
  • Confirm database type & version của từng hệ thống nguồn (MySQL? PostgreSQL? SQL Server?)
  • Confirm hệ thống nguồn nào có API/webhook, hệ thống nào chỉ export DB/CSV
  • Confirm data volume ước tính: số khách, số giao dịch/ngày, số event/ngày

Schema

  • Review danh sách fields thực tế từ POS/CRM/ERP → adjust PG + CH schema
  • Xác nhận naming convention: tiếng Việt hay tiếng Anh cho business terms
  • Xác nhận timezone convention: UTC hay Asia/Ho_Chi_Minh
  • Xác nhận PG connection pooling: PgBouncer hay built-in?
  • Xác nhận backup strategy: PG (pg_dump / WAL archiving) + CH (clickhouse-backup)
